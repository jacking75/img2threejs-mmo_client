01 · EXECUTIVE DECISION

권장 구현안

기존 게임 런타임에 에이전트를 넣지 않고 개발 모드에만 편집 경로를 추가한다.

MVP의 핵심은 범용 3D 모델러가 아니다.

갤러리에서 리소스와 부품을 선택하면 편집툴이 assetId, 명명된 노드 경로, bounds, transform, 카메라, 스크린샷, 소유 소스 파일을 하나의 편집 컨텍스트로 묶는다. 사용자는 “이 늑대의 귀를 조금 더 길고 뒤로 젖혀 달라”처럼 지시하고, Codex가 계획을 먼저 제시한 뒤 승인된 경우에만 절차형 팩토리 코드를 수정한다. Vite HMR이 같은 선택과 카메라를 복원해 결과를 즉시 보여준다.

D-01

별도 편집 모드

?mode=editor와 dev:editor 스크립트로 게임 런타임과 분리한다.

D-02

로컬 ACP 호스트

브라우저 대신 Node 프로세스가 stdio ACP 클라이언트와 비밀 보관을 담당한다.

D-03

계획 후 적용

첫 요청은 읽기 전용 분석, 두 번째 명시 승인 뒤에만 파일 쓰기와 명령 실행을 연다.

D-04

소스가 정본

뷰포트 transform은 초안이다. 영속 변경은 Codex가 팩토리 코드를 수정해야 확정된다.

02 · REPOSITORY BASELINE

현재 기준선

이미 있는 자산을 재사용하되 갤러리 단일 파일의 책임은 먼저 분리해야 한다.

655종 카탈로그

src/assets/catalog.ts가 캐릭터·NPC·동물·몬스터·아이템·월드 리소스를 하나의 AssetDefinition[]으로 노출한다.

안정적인 부품 이름

최근 리소스는 이름 있는 분리 부품, 소켓, collider 의도, destruction group, deep dispose 계약을 제공한다.

읽기 전용 갤러리

AssetGallery.ts에 카탈로그 UI·Three.js 장면·카메라·선택·dispose가 함께 있어 편집툴 전에 공용 뷰포트로 추출해야 한다.

개발 서버

Vite는 127.0.0.1:4173에 바인딩된다. 로컬 호스트 미들웨어와 HMR을 연결하기 좋은 기준선이다.

검증 파이프라인

ESLint, Vitest, TypeScript build, Playwright E2E가 준비되어 있고 현재 21파일 86개 단위 테스트가 있다.

편집 계약 부재

현재 AssetDefinition.create()는 인자를 받지 않는다. “어떤 파일의 어떤 파라미터가 어느 부품을 만든다”는 명시적 소유권 정보가 없다.

03 · SCOPE

범위와 설계 원칙

이번 도구는 로컬 개발 생산성을 높이되 게임 마일스톤의 오프라인 경계를 넓히지 않는다.

MVP에 포함한다

  • 655종 검색·분류·즐겨찾기와 최근 편집 기록을 제공한다.
  • Orbit, 정면/측면/후면 프리셋, wireframe, bounds, socket, collider 표시를 제공한다.
  • 명명된 THREE.Object3D 부품 트리와 클릭 선택·강조·transform 읽기를 제공한다.
  • 선택 부품과 캡처를 ACP 요청에 첨부하고 Codex 스트리밍 응답을 보여준다.
  • 계획 검토, 권한 승인, 파일 diff, 명령 로그, 검사 결과를 한 타임라인에 남긴다.
  • 승인된 소스 변경 뒤 현재 asset·part·camera를 복원해 재렌더한다.

MVP에서 제외한다

  • 정점·엣지·면 단위의 범용 메시 편집과 sculpt 브러시는 구현하지 않는다.
  • Blender, GLB rig, skin weight, animation curve를 브라우저에서 직접 수정하지 않는다.
  • 클라우드 호스팅, 원격 접속, 다중 사용자 동시 편집, 계정 서버를 추가하지 않는다.
  • 에이전트가 자동 commit, push, 패키지 설치, 범위 밖 파일 수정을 하지 않는다.
  • 게임 플레이용 도메인 상태에 편집기 세션·대화 상태를 섞지 않는다.
  • ACP v2 초안 기능에 의존하지 않고 v1 기준으로 고정한다.

브라우저와 에이전트 프로세스를 분리한다

브라우저는 stdio와 비밀을 직접 다루지 않는다. Node 호스트가 ACP 클라이언트다.

06 · ACP CONVERSATION

대화와 변경의 상태 모델

한 번의 자연어 요청을 분석과 적용으로 나누어 권한 경계를 눈에 보이게 만든다.

context-ready→ planning→ awaiting-approval→ applying→ reloading→ verifying→ completed /failed · cancelled
단계브라우저로컬 ACP 호스트Codex사용자 제어
연결SSE 구독, 상태 표시codex-acp spawn, ACP initialize/auth세션 capability와 인증 방법 제공로그인 또는 API key 방식을 선택한다.

계획스트리밍 응답·도구 이벤트 표시ACP session/prompt와 update 중계읽기 전용으로 소스 위치·변경안·검사 제시적용, 수정 요청, 취소 중 하나를 고른다.
적용승인 모달과 diff 타임라인 표시권한 요청 전달, 범위 정책 검사승인된 파일 편집과 좁은 검사 실행파일·명령별 요청을 허용하거나 거부한다.
검증선택·카메라 복원, 전후 캡처 비교HMR 상태와 검사 결과 수집결과 요약과 잔여 리스크 보고완료 승인 또는 추가 보정을 요청한다.

프로토콜 선택 근거다. 공식 OpenAI 문서는 제품 내 깊은 통합에 Codex App Server를 권장하고 인증·대화 기록·승인·스트리밍 이벤트를 제공한다고 명시한다. ACP Registry의 Codex 어댑터는 이 App Server를 실행해 ACP 요청과 Codex 이벤트를 상호 변환한다. 따라서 편집툴은 ACP v1 클라이언트로 구현하면서 Codex 내부 프로토콜 결합을 어댑터 뒤로 숨길 수 있다.

07 · DATA CONTRACTS

선택과 요청을 직렬화한다

Three.js 객체를 대화 상태에 넣지 않고 안정적인 ID와 숫자 데이터로 경계를 만든다.

브라우저 → 호스트 편집 컨텍스트

interface EditorSelection {
  assetId: string;
  category: AssetDefinition["category"];
  sourceFiles: readonly string[];
  part: {
    nodePath: readonly string[];
    nodeName: string;
    partKey?: string;
    localTransform: SerializableTransform;
    worldBounds: SerializableBox3;
  } | null;
  camera: CameraSnapshot;
  overlays: OverlayState;
  capturePath?: string;
}

편집 요청과 결과

interface ResourceEditRequest {
  requestId: string;
  sessionId: string;
  instruction: string;
  selection: EditorSelection;
  mode: "plan" | "apply";
  allowedWriteRoots: readonly string[];
  validation: readonly ValidationTarget[];
}

type EditStatus =
  | "planning" | "awaiting-approval"
  | "applying" | "reloading"
  | "verifying" | "completed"
  | "failed" | "cancelled";

명시적 소스 소유권

개발 전용 manifest가 assetId → sourceFiles → focusedTests를 매핑한다. 에이전트가 문자열 검색으로 소유 파일을 추측하지 않게 한다.

안정적인 partKey

node.name만으로 부족한 경우 카탈로그별 partKey를 추가한다. 재생성 뒤에도 같은 부품을 다시 선택할 수 있어야 한다.

세션 영속성

브라우저에는 UI 배치와 마지막 선택만 저장한다. ACP thread/session ID와 로그는 로컬 호스트가 프로젝트별 개발 캐시에 저장한다.

09 · DELIVERY PHASES

단계별 구현 계획

각 Phase는 독립적으로 실행 가능하고 검증 가능한 상태를 유지한다.

Phase 0

계약과 spike

ACP 연결과 리소스 소유권을 코드 변경 전에 고정한다.

  • ADR: 로컬 전용, ACP v1, plan/apply 2단계, 자동 commit 금지
  • codex-acp initialize/auth/session smoke script
  • 대표 리소스 5종의 asset→source→part mapping 검증
  • 가짜 ACP agent와 실제 adapter 모두 handshake한다.
  • Windows에서 subprocess 종료와 재시작이 누수 없이 동작한다.
  • 실패하면 UI 구현으로 넘어가지 않는다.
Phase 1

갤러리 기반 분리

읽기 전용 갤러리를 공용 뷰포트와 카탈로그 패널로 나눈다.

  • AssetViewport, frame, overlays, dispose 추출
  • 기존 ?mode=gallery 화면과 동작 보존
  • 편집 모드 진입점과 빈 shell 추가
  • 기존 갤러리 E2E가 동일하게 통과한다.
  • 리소스 전환 100회 후 geometry/material 누수가 없다.
  • main.ts는 조합만 담당한다.
Phase 2

읽기 전용 편집기

부품을 안전하게 지목하고 컨텍스트를 만들 수 있게 한다.

  • outliner, raycast 선택, highlight, TransformControls 읽기/초안
  • socket·collider·bounds·axis overlay와 뷰 프리셋
  • EditorSelection 직렬화와 캡처 생성
  • 대표 동물·몬스터·소품의 주요 part가 클릭/트리 양쪽에서 일치한다.
  • 초안 transform은 소스 저장으로 오해되지 않게 표시한다.
  • 재생성 뒤 partKey로 선택을 복원한다.
Phase 3

로컬 편집 호스트

브라우저와 파일·프로세스 권한 사이의 신뢰 경계를 만든다.

  • same-origin API, SSE, session token, health endpoint
  • workspace root·path allowlist·dirty baseline 정책
  • 브라우저 캡처를 개발 캐시에 저장
  • 127.0.0.1 외 바인딩을 거부한다.
  • root 밖 경로, traversal, symlink 탈출을 거부한다.
  • 토큰·환경 변수가 브라우저 payload와 로그에 나타나지 않는다.
Phase 4

ACP 읽기 전용 대화

선택 컨텍스트로 Codex와 대화하되 쓰기는 아직 막는다.

  • ACP SDK와 codex-acp exact version 추가
  • initialize, authenticate, new/load session, prompt, cancel
  • text·plan·tool·usage·error update를 UI 이벤트로 매핑
  • “선택한 부품 설명” 요청이 정확한 asset/part/source를 언급한다.
  • 새로고침 뒤 세션을 복원한다.
  • agent mode가 read-only임을 UI와 정책 테스트가 보장한다.
Phase 5

승인된 적용 루프

분석 결과를 사용자가 확인한 뒤 제한된 코드 변경을 허용한다.

  • plan→apply 전환, approval broker, 명령·파일 요청 UI
  • 파일 diff와 ACP tool event 타임라인
  • 관련 없는 기존 변경 감지와 충돌 경고
  • 승인 전에는 tracked 파일 byte가 바뀌지 않는다.
  • 허용 root 밖 요청과 새 의존성 설치는 거부된다.
  • 거부·취소 뒤 agent와 child process가 정상 종료된다.
Phase 6

HMR과 전후 비교

코드 변경을 같은 시점·같은 각도에서 즉시 판단한다.

  • asset module 변경 감지, 안전 dispose, 인스턴스 재생성
  • asset·part·camera·overlay 복원
  • before/after slider, 승인 캡처, 요청별 변경 묶음
  • HMR 뒤 선택이 다른 부품으로 이동하지 않는다.
  • WebGL 컨텍스트·geometry·material 누수가 없다.
  • 컴파일 실패 시 마지막 정상 뷰와 오류를 함께 보여준다.
Phase 7

검증과 운영 완성

도구 자체와 에이전트 변경의 품질 증거를 표준화한다.

  • focused test→lint→unit→build→E2E 단계 실행
  • 검사 취소·재시도·타임아웃·구조화 결과
  • README, 운영 절차, 문제 해결, 버전 업데이트 정책
  • 최종 E2E가 선택→대화→승인→수정→HMR→검증을 통과한다.
  • 실제 브라우저에서 대표 3종을 수동 검수한다.
  • ACP adapter 업데이트는 smoke suite 통과 뒤에만 허용한다.

11 · SECURITY & APPROVAL

로컬 도구여도 기본 거부로 설계한다

에이전트가 소스를 수정하므로 네트워크·파일·명령·비밀 경계를 UI에 드러내야 한다.

프로세스 경계

호스트는 127.0.0.1에만 바인딩하고 임의 Origin을 거부한다. 브라우저 종료·서버 종료 시 child process를 정리한다.

비밀 경계

ChatGPT 인증과 API key는 adapter/host 프로세스에만 존재한다. 브라우저는 인증 상태 enum만 받는다.

파일 경계

기본 쓰기 root는 src/assets/**, 관련 test, 문서 로그로 제한한다. 매 요청에서 resolved absolute path를 재검증한다.

명령 경계

검사 명령은 registry에 정의된 argv만 실행한다. 셸 문자열 연결, 임의 pipe, redirection을 허용하지 않는다.

변경 경계

시작 시 Git dirty baseline을 캡처하고 기존 사용자 변경과 겹치면 적용을 중단한다. 자동 reset·checkout·commit·push는 없다.

승인 경계

요청에는 이유, 대상 파일/명령, 예상 효과, 만료 시간이 표시된다. 거부가 기본값이며 세션 전체 허용은 제공하지 않는다.

13 · FINAL ACCEPTANCE

최종 완료 조건

다음 항목이 실제 브라우저에서 모두 재현될 때만 편집툴 MVP를 완료로 판정한다.

  1. npm run dev:editor 한 명령으로 로컬 편집 UI와 ACP 호스트가 함께 시작된다.
  2. 현재 655종을 카테고리·이름·ID·태그로 검색하고 어떤 리소스든 뷰포트에 표시할 수 있다.
  3. 뷰포트나 outliner에서 이름 있는 부품을 선택하면 같은 partKey, transform, bounds, source ownership이 표시된다.
  4. 선택한 리소스·부품·카메라·캡처가 ACP 요청에 포함되고 Codex가 그 대상을 정확히 되짚어 설명한다.
  5. 첫 요청은 읽기 전용 계획만 만들며 사용자 승인 전에는 tracked 파일과 외부 상태가 변하지 않는다.
  6. 승인 후 허용된 파일만 수정되고 Vite HMR이 같은 리소스·부품·카메라를 복원해 결과를 보여준다.
  7. before/after 캡처, 파일 diff, 명령 로그, focused test와 전체 품질 gate 결과를 요청 하나로 추적할 수 있다.
  8. 페이지 새로고침이나 호스트 재연결 뒤 최근 ACP 세션과 편집 대상을 안전하게 복원할 수 있다.
  9. 권한 거부·에이전트 취소·컴파일 오류·child crash에서 작업 트리와 UI가 복구 가능한 상태로 남는다.
  10. 자동 commit·push, 원격 공개, 범위 밖 파일 쓰기, 브라우저로의 비밀 전달이 발생하지 않는다.
