# 상세 구현 계획 — 애니메 필드 RPG 프로토타입

## 1. 목표와 범위

스타일화된 판타지 3인칭 RPG의 로컬·오프라인·데스크톱 브라우저 세로 기능 묶음을
구현한다. 플레이어는 약 5등신 일본 애니메이션 풍 캐릭터를 만들고, 체형 표현과
클래스를 선택한 뒤 **필드 입장**을 누른다. 작은 필드를 이동하고, 인벤토리를 열어
의상과 검을 교체하며, 검 공격 애니메이션을 실행한다.

이 문서는 의도적으로 **클라이언트 전용 프로토타입**만 다룬다. 네트워킹, 서버 권한,
로그인, 원격 데이터, 매치메이킹, 다른 플레이어, 적, 피해량, 퀘스트는 포함하지 않는다.

## 2. 플레이어 관점의 사양

### 2.1 캐릭터 생성

생성 화면은 다음을 제공한다.

- 캐릭터 이름 입력: 2~16자, 로컬 표시용.
- 체형 표현: `feminine` 또는 `masculine`. 스타일화된 기본 몸, 얼굴/머리카락 프리셋,
  기본 팔레트를 바꾸지만 입력과 전투 로직은 바꾸지 않는다.
- 클래스: `warrior`, `mage`, `ranger`.
- idle 애니메이션 또는 idle 포즈가 보이는 실시간 3D 미리보기.
- 선택 클래스의 짧은 설명과 시작 장비.
- 이름과 클래스가 유효할 때만 활성화되는 **필드 입장** 버튼.

초기 클래스 차이는 표현과 시작 장비 차이로만 한정한다.

| 클래스 | 시작 의상 | 시작 무기 | 프로토타입에서의 역할 |
| --- | --- | --- | --- |
| 전사 (`warrior`) | 철제/파란 튜닉 | 연습용 검 | 검 교체를 검증하는 주 경로 |
| 마법사 (`mage`) | 남색 로브 | 견습생 검 | 이번 마일스톤에서는 동일한 검 시스템 사용 |
| 궁수 (`ranger`) | 녹색 여행복 | 짧은 검 | 이번 마일스톤에서는 동일한 검 시스템 사용 |

하나의 무기 구현을 유지하면 세 개의 별도 전투 시스템을 피할 수 있다. 지팡이와 활
전투는 이 세로 기능 묶음 이후 동일한 장비 소켓 API 위에 추가한다.

### 2.2 필드

- 잔디, 길, 바위, 나무, 단순 충돌 장애물이 있는 약 80 × 80 월드 단위의 필드.
- 5등신 셀 셰이딩 아바타와 3인칭 추적 카메라.
- 카메라 방향 기준 이동: `WASD`, `Shift`로 달리기.
- 마우스 드래그로 카메라 회전. 초기에는 카메라 충돌이 필요 없다.
- HUD에는 캐릭터 이름, 클래스, 장착 검, 짧은 조작 안내를 표시한다.
- 적과 피해량 계산은 없다. 공격은 시각적 피드백만 제공한다.

### 2.3 인벤토리와 장비

`I` 키는 필드를 내리지 않고 인벤토리 오버레이를 열고 닫는다.

필수 슬롯은 다음과 같다.

| 슬롯 | 필수 콘텐츠 | 첫 세로 기능 묶음의 렌더링 방식 |
| --- | --- | --- |
| 무기 | 연습용 검, 달빛 검 | `hand.R`에 장착하는 독립 `THREE.Group` |
| 의상 | 시작 의상, 여행자 의상 | 팔레트/재질 및 모듈형 몸 변화 |
| 머리 | 없음, 시작 모자 | `head`에 장착하는 선택적 독립 그룹 |

사용자가 소유한 아이템을 선택하면 직렬화 가능한 장비 상태와 아바타의 외형이 즉시
업데이트된다. 아이템은 삭제·소비·네트워크 전송되지 않는다.

### 2.4 공격

- 인벤토리가 닫혀 있을 때 마우스 왼쪽 버튼 또는 `F`로 `attack_1`을 시작한다.
- 공격은 설정 가능한 고정 시간 동안 지속하며, 짧은 입력 잠금 시간을 가진다.
- 장착한 검은 공격 중에도 계속 `hand.R`에 붙어 있어야 한다.
- 피격 판정, 피해량, 대상, 효과는 요구하지 않는다. 짧은 검기 효과는 검 휘두르기가
  효과 없이도 충분히 읽힌 뒤에만 추가한다.

## 3. 아키텍처 결정

### 3.1 기술 스택

| 관심사 | 선택 | 이유 |
| --- | --- | --- |
| 빌드/개발 서버 | Vite | 최소한의 TypeScript 브라우저 작업 흐름 |
| 언어 | TypeScript strict mode | 장비와 상태 계약을 명확히 표현 |
| 3D | Three.js | 브라우저 WebGL 씬, 애니메이션, 그룹 |
| UI | DOM + CSS | 메뉴 규모가 작아 UI 프레임워크가 불필요 |
| 테스트 | Vitest, 이후 Playwright E2E 스모크 테스트 | 순수 상태와 보이는 플레이 흐름을 각각 검증 |
| 저장 | `localStorage` | 백엔드 없이 로컬 영속성 충족 |

### 3.2 런타임 상태의 소유권

정본 상태는 직렬화 가능하게 유지하고 Three.js와 독립시킨다.

```ts
type BodyPresentation = "feminine" | "masculine";
type CharacterClass = "warrior" | "mage" | "ranger";
type EquipmentSlot = "weapon" | "outfit" | "head";
type AnimationState = "idle" | "run" | "sprint" | "attack_1";

interface CharacterProfile {
  version: 1;
  name: string;
  body: BodyPresentation;
  classId: CharacterClass;
  ownedItemIds: string[];
  equipped: Record<EquipmentSlot, string | null>;
}
```

`src/domain`은 이 상태를 검증하고 전이시킨다. `src/render`는 상태를 관찰해 Three.js
객체를 생성/제거하고, 활성 아이템 ID를 팩토리에 연결한다. 이 분리는 나중에 온라인
기능을 추가하더라도 UI와 에셋 모듈 전체를 다시 쓰지 않게 한다.

### 3.3 아바타와 소켓 계약

먼저 다음 조건을 만족하는 모듈형 프리미티브 아바타를 만든다.

- 머리 높이를 기준 단위로 삼는다.
- 전체 키는 약 다섯 머리 높이로 구성한다.
- 큰 머리, 작은 몸통, 짧은 팔다리, 읽기 쉬운 셀 셰이딩 색을 사용한다.
- 노드/소켓 이름은 정확히 `root`, `head`, `hand.R`, `hand.L`, `back`으로 한다.

초기 아바타는 단순한 팔다리 그룹 회전으로 움직일 수 있다. 이후 리깅된 GLB 아바타를
넣을 때는 어댑터를 통해 같은 부착점을 보존한다. 장비를 숫자 자식 인덱스나 광범위한
이름 탐색에 묶지 않는다.

강체 무기 팩토리 계약은 다음과 같다.

```ts
export interface EquipmentVisual {
  readonly itemId: string;
  readonly slot: "weapon" | "outfit" | "head";
  create(): THREE.Group;
}

// 무기 팩토리: 그립은 원점, 로컬 축을 문서화, 전역 씬 접근 금지.
```

나중에 생성한 무기는 `img2threejs`의 TypeScript 결과를 이 인터페이스 뒤로 어댑트한다.
해당 에셋은 게임 루프를 호출하거나 카메라를 조작하거나 장비 상태를 소유해서는 안 된다.

### 3.4 애니메이션 상태 우선순위

작고 명시적인 상태 선택기를 사용한다.

```text
attack_1 활성 상태       → attack_1
Shift + 달리기 임계값 이상 → sprint
이동 임계값 이상          → run
그 외                    → idle
```

`attack_1`은 설정된 종료 시점까지 우선한다. 공격 중에도 입력을 읽을 수는 있지만, 공격
포즈를 run으로 일찍 교체해서는 안 된다.

### 3.5 저장

- 캐릭터 확정 직후와 성공적인 장비 변경마다 저장한다.
- 앱 시작 시 `anime-field-rpg.profile.v1` 같은 하나의 키를 읽는다.
- 파싱한 데이터를 검증한다. 잘못되었거나 오래된 저장은 충돌 대신 캐릭터 생성으로
  안전하게 되돌린다.
- 테스트를 위해 생성 화면에 작은 **로컬 캐릭터 초기화** 동작을 제공한다.

## 5. 단계별 구현 계획

각 단계는 Codex CLI에 보내는 별도 요청 하나다. 다음 단계로 가기 전, 그 단계에서
명시한 검사를 완료한다.

### Phase 0 — 스캐폴드와 프로젝트 계약

**목표:** 계획만 있는 저장소를 실행 가능한 빈 TypeScript/Three.js 애플리케이션으로
전환한다.

**구현 항목**

1. 이 저장소 루트에 Vite `vanilla-ts` 템플릿을 초기화한다.
2. Three.js, 린트 도구, Vitest를 추가하고 `dev`, `build`, `lint`, `test`, `test:e2e`
   패키지 스크립트를 만든다. `test:e2e`는 Phase 9 전까지 문서화된 자리표시자여도 된다.
3. `AGENTS.md`, `README.md`, 이 계획 문서는 보존한다.
4. Vite 시작 화면을 루트 DOM 요소와 캔버스 호스트가 있는 앱 셸로 교체한다.

**인수 검사**

- `npm run build`가 성공한다.
- `npm run lint`가 성공한다.
- 최소 하나의 기본 스모크 테스트와 함께 `npm run test`가 성공한다.
- 개발 서버에서 비어 있지만 의도적으로 스타일을 준 앱 셸이 열린다.

### Phase 1 — 도메인 모델과 로컬 저장

**목표:** 렌더링 전에 캐릭터·장비 상태를 신뢰할 수 있게 만든다.

**구현 항목**

1. 체형 표현, 클래스, 아이템 카탈로그, 장비 슬롯, 프로필 타입을 추가한다.
2. 세 클래스와 최소 두 종류의 검/의상 카탈로그 항목을 정의한다.
3. 기본 프로필 생성, 이름 검증, 소유 아이템 장착, 시작 장비 도출, 저장 직렬화/복원
   순수 함수를 만든다.
4. 비정상 저장 복구가 있는 `localStorage` 어댑터를 구현한다.

**테스트**

- 클래스 선택이 문서에 적힌 시작 장비를 부여한다.
- 소유하지 않은 아이템 장착은 거부된다.
- 검 장착은 무기 슬롯만 변경한다.
- 잘못된 저장 JSON 또는 지원하지 않는 버전은 안전하게 캐릭터 생성으로 시작한다.

### Phase 2 — 캐릭터 생성 화면

**목표:** 아직 3D 필드가 없어도 플레이어가 캐릭터를 선택하고 확정하게 한다.

**구현 항목**

1. 이름, 체형 표현 카드, 클래스 카드, 실시간 시작 장비 요약, 초기화 동작, 비활성/활성
   필드 입장 버튼이 있는 타이틀/생성 DOM 화면을 만든다.
2. 유효한 프로필을 확정하면 즉시 저장한다.
3. 유효 저장이 있을 때 생성 화면을 몰래 건너뛰지 말고 **계속하기**와 **새 캐릭터 생성**을
   제공한다.

**수동 인수 검사**

- 필드 입장 전 이름 검증이 보인다.
- 각 클래스를 선택하면 설명과 시작 장비가 바뀐다.
- 새로고침 후 마지막으로 확정한 프로필이 유지된다.

### Phase 3 — Three.js 필드와 3인칭 카메라

**목표:** UI에 숨은 게임플레이 의존성 없이 읽기 쉬운 스타일화된 필드를 렌더링한다.

**구현 항목**

1. 렌더러, 씬, 카메라, 크기 변경 처리, 시계, 애니메이션 루프를 설정한다.
2. 잔디 평면, 길, 방향 조명, 반구 조명, 나무/바위 몇 개, 안개, 하늘색으로 80 × 80
   셀 셰이딩 필드를 만든다.
3. 테스트 대상에 대해 안정적 오프셋을 유지하는 회전/추적 카메라를 구현한다.
4. 플레이어 이동 전에도 나무와 바위의 기본 충돌 볼륨을 추가한다.

**수동 인수 검사**

- 창 크기 변경 시 화면이 찌그러지거나 검은 캔버스가 남지 않는다.
- 카메라가 테스트 마커를 추적/회전하며 계속 바라본다.
- 목표 카메라 거리에서 필드가 읽기 쉬운 상태로 유지된다.

### Phase 4 — 임시 애니메 아바타와 이동

**목표:** 필드에 애니메 비율 캐릭터를 두고 움직인다.

**구현 항목**

1. 5등신 비율과 필수 소켓을 가진 `createPlaceholderAvatar`를 이름 있는 그룹으로 만든다.
2. 선택한 체형 표현과 클래스 팔레트를 렌더링한다.
3. WASD 입력을 카메라 상대 이동으로 변환하고 `Shift`는 속도를 높인다.
4. 필드 경계와 단순 원/AABB 장애물에 대해 이동을 해결한다.
5. idle, run, sprint 절차적 애니메이션(팔다리 흔들기/몸통 상하 움직임)을 구현한다.

**수동 인수 검사**

- `WASD`가 월드 고정축이 아니라 화면 방향을 기준으로 움직인다.
- 아바타가 필드 밖으로 나가거나 최소 하나의 나무/바위를 통과할 수 없다.
- 회전과 달리기 중에도 카메라가 부드럽다.
- idle/run/sprint 전환이 튀지 않고 보인다.

### Phase 5 — 장비 카탈로그와 검 부착

**목표:** 향후 모든 아이템에 적용될 동일한 상태→렌더 경로로 검 교체를 보이게 한다.

**구현 항목**

1. 연습용 검과 달빛 검을 독립 `THREE.Group` 팩토리로 만든다.
2. 활성 무기 팩토리를 아바타의 정확한 `hand.R` 소켓에 부착한다.
3. 아바타 전체를 다시 만들지 않고 이전 외형을 dispose/제거한 후 새 외형을 추가하는
   `EquipmentRenderer`를 만든다.
4. `outfit` 슬롯에 따라 선명하게 구분되는 시작 의상·여행자 의상 팔레트/모듈형 메시
   변화를 구현한다.
5. 반복 교체 뒤에도 중복 무기나 끊어진 참조가 없도록 한다.

**테스트와 수동 인수 검사**

- 순수 장비 테스트가 유효/무효 슬롯 변경을 다룬다.
- 검을 바꾸면 외곽선이 달라지고 이동 중에도 손 소켓 부착을 유지한다.
- 의상을 바꾸면 색/형태가 즉시 바뀐다.
- 반복 교체 후 씬에 유령 무기가 남지 않는다.

### Phase 6 — 인벤토리 UI

**목표:** 소유 장비를 사용하기 쉬운 게임 내 패널로 노출한다.

**구현 항목**

1. `I`로 열고 `I`/`Esc`로 닫는 HUD와 인벤토리 오버레이를 추가한다.
2. 아이템을 슬롯별로 그룹화하고 선택/장착 상태를 보이며, 사용할 수 없는 아이템은
   비활성화한다.
3. 클릭 처리에서 씬을 직접 바꾸지 않는다. 도메인 액션 → 저장 → 렌더 갱신 순으로
   선택을 처리한다.
4. 인벤토리가 열려 있는 동안 이동 입력은 멈추되, 뒤의 필드는 계속 렌더링한다.

**수동 인수 검사**

- 인벤토리를 열어도 아바타/카메라 위치가 초기화되지 않는다.
- 마우스 클릭으로 두 검과 두 의상을 모두 장착할 수 있다.
- Escape는 패널을 닫고 이동 조작을 되돌린다.
- 새로고침 후 장착 아이템 ID와 보이는 상태가 유지된다.

### Phase 7 — 검 공격 애니메이션

**목표:** 전투 시스템을 추가하지 않고도 반응성이 좋고 읽기 쉬운 공격을 만든다.

**구현 항목**

1. `attack_1` 상태, 시작 제한, 쿨다운, 입력 매핑을 추가한다.
2. 장착 검이 의도적인 가로/대각선 베기를 그리도록 몸통, 오른팔/소켓, 선택적 루트
   전진 움직임을 애니메이션한다.
3. `setTimeout`이 아닌 delta time 기반의 애니메이션 타임라인을 사용한다.
4. 공격 포즈가 run 애니메이션에 덮어써지지 않도록 공격 우선순위를 보장한다.
5. 공격이 끝난 뒤 현재 이동 입력에 따라 idle/run/sprint로 돌아간다.

**테스트와 수동 인수 검사**

- `animationState` 테스트가 공격 우선과 이동 애니메이션 복귀를 증명한다.
- 인벤토리가 닫혀 있을 때만 마우스 왼쪽 버튼/F가 공격을 실행하며, 열려 있을 때는
  실행하지 않는다.
- 두 검 모두를 시험한다. 전체 휘두르기 동안 `hand.R` 정렬을 유지해야 한다.
- 공격 중 `W`를 누르고 있으면 휘두르기가 끝난 뒤에만 run으로 돌아온다.

### Phase 8 — 시각 다듬기와 img2threejs 에셋 어댑터

**목표:** 세로 기능 묶음을 불안정하게 만들지 않고 표현을 개선한다.

**구현 항목**

1. 5등신 실루엣에 맞게 셀 셰이딩, 성능이 허용되면 외곽선, 팔레트, 안개, 카메라
   프레이밍을 조정한다.
2. 공격을 더 명확히 만들 때만 작은 검기 효과를 추가한다.
3. 검토한 `img2threejs` 무기 결과물을 위한 문서화된 어댑터 템플릿을 추가한다.
4. 원본 판타지 검 하나를 생성하거나 직접 만들고, TypeScript 팩토리를 검토한다.
   그립/소켓 계약을 지킨 뒤에만 세 번째 카탈로그 무기로 등록한다.

**수동 인수 검사**

- 캐릭터, 의상, 검이 필드를 배경으로도 명확히 보인다.
- 생성/추가한 검에 전역 상태 부작용이 없고 정상적으로 교체된다.
- `npm run build` 뒤 브라우저 콘솔에 누락 에셋 요청이 없다.

### Phase 9 — 종단 간 검증과 인수인계

**목표:** 프로토타입을 반복 시연할 수 있고 다음 기능에 안전하게 넘길 수 있게 한다.

**구현 항목**

1. 브라우저 스모크 테스트를 추가한다: 전사 생성 → 필드 입장 → 이동 → 인벤토리 열기
   → 달빛 검 장착 → 공격.
2. 조작이 바뀌었다면 `README.md`에 선택적 수동 체크리스트를 추가한다.
3. 사용하지 않는 시작 파일과 개발용 콘솔 출력을 제거한다.
4. 최종 패키지 버전과 알려진 한계를 기록한다.

**릴리스 인수 검사**

1. 로컬 저장을 지운다.
2. 원하는 체형 표현으로 이름 있는 전사를 만든다.
3. 필드에 입장해 이동, 달리기, 카메라 회전, 장애물 충돌을 확인한다.
4. 인벤토리에서 달빛 검과 여행자 의상을 장착한다.
5. 정지 상태와 달리기 상태에서 공격한다.
6. 새로고침하고 계속하기를 선택한다. 이름, 클래스, 의상, 검이 맞는지 확인한다.
7. `npm run lint`, `npm run test`, `npm run build`를 모두 성공시킨다.

## 6. 에셋 제작 경로

### 첫 플레이 가능 빌드

필수 시각 요소는 모두 절차적 프리미티브로 구현한다. 이렇게 하면 아트와 리깅 작업이
이동·인벤토리 구현을 막지 않는다.

### 개선 경로

1. 프리미티브 아바타를 직접 제작했거나 적절히 라이선스가 확인된 리깅 GLB로 교체한다.
2. 실제 스켈레톤 본 이름을 `head`, `hand.R`, `hand.L`, `back` 소켓으로 매핑하는
   `AvatarAdapter`를 만든다.
3. `GLTFLoader`로 idle/run/attack 클립을 불러오고 동일한 애니메이션 상태 기계에
   매핑한다.
4. 모든 메시가 동일한 아마추어와 호환 가능한 스킨 웨이트를 사용할 때만 의상 팔레트를
   별도 스키닝 메시로 교체한다.
5. `img2threejs`는 강체 장비에만 사용한다. 검토한 소스 팩토리는
   `src/assets/equipment/generated/`에 두고, 참조/제작 메모는 공개 런타임 에셋 밖에
   보존한다.

## 7. 비목표와 보류한 결정

다음 항목은 잊은 것이 아니라 의도적으로 보류한다.

- 네트워크 프로토콜, 서버 권한, 동기화, 부정행위 방지, 인증, 영구 계정, 데이터베이스,
  매치메이킹, 채팅.
- 적, 타기팅, 피격 상자, 피해 수치, 전리품, 퀘스트, 지도, 사운드, 고비용 파티클 효과,
  버전 1 이후의 저장 마이그레이션.
- 최종 캐릭터 리그, 블렌드셰이프, 천 시뮬레이션, 세부 얼굴 커스터마이징, 고급 렌더러/
  포스트 프로세싱, 모바일 지원, 접근성 키 재매핑.
- 클래스별 지팡이/활 전투. 카탈로그는 미래 무기 유형을 허용하지만, 지금은 장비
  파이프라인을 증명하기 위해 검만 필요하다.
